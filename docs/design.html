Router–Judge Architecture on Claude Fable & Opus

Nate Jones' "Ringer" pattern reframes multi-agent design around a simple discipline: a strong model plans once and never touches the work; a swarm of cheap models burns the tokens; nothing ships without a mechanical check the model can't talk its way past. This document adapts that pattern to a concrete harness — Claude Fable 5 or Opus 4.8 as the planner and judge, Sonnet 5 and Haiku 4.5 as disposable workers — and treats the four-question "agent test" as a literal gate a task must pass before any agent is spun up at all.

The rest of this document is organized as the eight components of that strategy, in the order you'd actually apply them: classify the task, respect its constraints, split its roles, architect the harness, aim it at the right work, and price it before you commit.

§1

Start with the agent test, not the tools

The question is never "can an agent do this" — nearly everything can be forced through an agent loop. The question is whether the task's shape justifies the coordination overhead. Four structural estimates, plus two economic dials, answer it in about a minute:

  • Size — does the task exceed what one agent can hold in context at full quality?
  • Independence — can the pieces be worked without coordinating with each other?
  • Separation of concerns — does correctness require a mind that didn't produce the work?
  • Checkability — is verifying an answer much cheaper than producing one?

Frequency and value are not a fifth structural question — they're the budget check that decides whether the trade is worth making at all, independent of shape.

§2

Respect the two hard limits

Every multi-agent design that actually works is an answer to one of two constraints. Designs that ignore them don't fail loudly — they fail quietly, or just burn money.

Constraint 1

Context / memory limit

A single agent's window fills up and quality degrades, even with compaction. Once a task is bigger, longer, or more heterogeneous than one context can hold coherently, splitting into independent chunks stops being optional.

Constraint 2

Validation limit

Multi-agent systems generate a pile of candidate answers. Without a strong, preferably automatic evaluator, the correct answer is in the pile but never identified — and every extra token spent generating alternatives was wasted.

In this harness, Constraint 1 is answered by the planner/worker split itself (§5): the planner never reads the full corpus, it writes a spec per unit of work and hands each unit to a worker with a clean, bounded context. Constraint 2 is answered by making the mechanical checker a first-class stage that runs before the judge ever sees the output — see §5.

§3

Spend tokens deliberately — attempts paired with evals

Two results frame the economics here. Stanford (2024) showed that giving a cheap model repeated attempts follows a smooth improvement curve — up to roughly 100 attempts — but only if something can pick the right answer out of the pile; past that point, more attempts without a checker are wasted compute. Separately, Anthropic's internal multi-agent research system found that the single biggest predictor of quality wasn't prompt cleverness, it was how much the system was allowed to think — token spend, spent in a structured way, beat a single frontier model working alone.

The operating rule that follows: use the multi-agent structure to buy more attempts and more perspectives, never as a way to smuggle in a bigger single model. And never generate a token you don't have a way to grade — an unchecked attempt is not an asset, it's a liability sitting in the pile.

Because planning and judging happen once per task (or once per batch) while worker calls happen once per unit of work, the harness naturally spends its expensive tokens on the smallest number of calls and its cheap tokens on the largest. A 40-document audit might make one Opus planning call, two hundred Sonnet worker calls, and a double-digit number of Opus judge calls on the outputs the mechanical checker couldn't resolve on its own — see §6 for the full assignment logic.

The OpenRouter tiers push the "spend tokens deliberately" logic one step further: a GLM/Kimi worker costs roughly a fifth to a third of Sonnet per token, at the price of noticeably less reliable structured output. That's only a good trade because the mechanical checker (§5) is already there to catch what it gets wrong — without it, routing the cheapest, least-supervised tier at your workers would be exactly the failure mode Stanford's research warns about: more attempts, no way to pick the right one out of the pile.

§4

Split work along roles, not along model capability

Some separations exist to fix a capability gap; the author/critic split exists to fix a conflict of interest — the same reason a company doesn't let the person who enters a payment also approve it. An agent gives you something a single human reviewer structurally can't: a mind that has genuinely never seen the draft, the product page, or the contract, on demand, for free.

Planner

Writes specs, never does the work

Reads the task shape, breaks it into independently checkable units, writes one spec per unit including its acceptance criteria. Never touches source material directly at scale.

Worker

Burns tokens, self-confidence ignored

Executes one spec: reads, extracts, drafts, codes. Attaches sources for every claim. Its own stated confidence is never trusted or scored.

Checker

Mechanical, deterministic, cheap

No model call at all where possible — schema validation, source-attachment checks, exit codes, regex, diff-against-ground-truth. Runs before the judge on every result.

Judge

Fresh eyes, never the author

Sees only the worker's output and the spec — never the worker's reasoning trace or confidence claims. Escalated to only for what the mechanical checker can't resolve.

The judge is deliberately kept ignorant of anything that would contaminate it: it doesn't see which worker produced the output, doesn't see prior attempts, and doesn't see the worker's self-assessment. That's the "fresh mind on demand" the brief calls for — de-biased review a human reviewer, who's usually seen the draft evolve, can't easily replicate.

§5

Architect the harness: planner, workers, checks, judge, scorecard

The concrete pipeline. The planner runs once. Workers run in parallel, as many as the task's independence score allows. Every result passes the mechanical checker before it's allowed near the judge — and the judge is a cost center reserved for what code can't decide.

Failures at either the checker or the judge loop back to a fresh worker call with the failure reason appended to the spec — never a bare retry of the same prompt. The OpenRouter worker tiers are opt-in per task; when enabled, the planner (not the task author) decides per unit whether it's routine and low-stakes enough to route there, and is told explicitly to avoid them for anything also flagged for judge review.

Retry semantics

A failed unit doesn't just re-run — it re-runs with the specific failure appended to its spec ("source citation missing for claim 3" / "schema validation failed: expected ISO date, got 'March 2024'"). This is the mechanism that turns Stanford's "more attempts" curve into something that actually converges: each retry is strictly better-informed than the last, not a fresh roll of the dice. Units are capped at a configurable retry ceiling (default 3) before they're marked needs-human and surfaced on the scorecard rather than silently dropped or silently accepted.

Why the judge is rationed

The judge model is the most expensive call in the system per invocation, and LLM judgment doesn't get cheaper by asking nicely — so the harness treats it as a scarce resource routed only to what the mechanical checker structurally cannot decide: tone, completeness of an argument, whether a summary actually represents its source. Anything with a mechanical answer — did the number parse, does the citation exist, did the test pass — never reaches the judge at all. This is the direct implementation of "checkability" from §1: the cheaper the check, the more attempts you can afford to burn before the check has to run.

§6

Model assignment logic

Model choice is a function of role, not a static default. The harness resolves it per call:

SituationModelWhy
Routine planning — decomposing a well-understood pileclaude-opus-4-8Strong enough to write correct specs; far cheaper than Fable per token.
Planning a genuinely novel or ambiguous task shapeclaude-fable-5Long-horizon reasoning and ambiguity-handling justify the premium — spent once, not per unit.
Default worker — extraction, drafting, coding, summarizingclaude-sonnet-5Near-Opus quality on agentic/coding work at a fraction of the cost; this is where token volume lives.
High-volume, low-complexity worker — classification, simple lookupsclaude-haiku-4-5Cheapest Anthropic tier; used when the spec is narrow enough that Haiku's ceiling doesn't matter.
Cheapest worker, opt-in — highest-volume, lowest-stakes units onlyz-ai/glm-5.2 / moonshotai/kimi-k2.7-codeRoughly a fifth to a third of Sonnet per token; the mechanical checker is what makes the reliability trade acceptable — see §5.
Default judge — most checker-escalated reviewclaude-opus-4-8Independent of the worker tier; good judgment at a cost the retry volume can sustain.
High-stakes judge — compliance, legal, financial sign-off unitsclaude-fable-5Escalate only the subset of units flagged as high-value by the task's own economics (§3).

Workers and the judge are never the same model instance or even the same conversation — no shared context, no shared cache, no way for the judge to have absorbed the worker's framing. That separation is enforced structurally in ringer/orchestrator.py, not by convention. The judge itself never routes to OpenRouter, regardless of which tier a worker used — the fresh-eyes review has to be at least as reliable as the thing it's grading.

§7

Know when to say no

A disciplined strategy says "no agents here" as often as "a team here." Three shapes reliably don't clear the bar:

Too small

Bounded, single-context tasks

Scheduling around one calendar, a single short document. One chat turn is the correct multi-agent system: zero agents.

Too subjective

Deep judgment calls

Which candidate to hire, which strategic bet to make, what to name the product. AI can research and structure the options; the decision stays human.

Too coupled

Entangled work with no natural split

Code changes that touch a single tight algorithm rarely decompose into independent units — organize into independent chunks first, or don't multi-agent it at all.

The agent test in §1 is the harness's own gate for this — a task that scores low on size, independence, and checkability, or whose frequency/value doesn't clear the token spend, is rejected at the planner's first pass rather than dutifully decomposed anyway.

§8

Implementation

The harness ships as a small, pluggable Python package — ringer/ — with no workload baked in. You supply a worker prompt/spec shape and a checker function; the package supplies the planner call, the parallel worker pool, the retry loop, the judge escalation, and the cost/pass-rate scorecard.

ringer/
  agent_test.py       # §1 — the four-question + economics scorer (same logic as the calculator above)
  models.py           # model IDs, pricing, providers, role → model resolution (§6)
  _client.py          # Anthropic call plumbing (planner/judge, and default/thrift workers)
  _openrouter_client.py  # OpenRouter call plumbing — open-weight worker tiers, opt-in
  planner.py          # Fable/Opus planning call → list of TaskSpec
  worker.py           # dispatches each spec to Anthropic or OpenRouter, spec in → WorkResult out
  checker.py          # pluggable deterministic Checker protocol + example checkers
  judge.py            # Opus/Fable judge call, fresh-context, checker-escalated only, Anthropic only
  orchestrator.py     # wires planner → workers → checker → judge → retry → scorecard
  scorecard.py        # SQLite-backed run ledger + CLI report
  cli.py              # `ringer run task.yaml`
examples/
  extract_invoices/  # a worked "pile of documents" example end to end, with an OpenRouter variant

See the repository README for setup and a runnable example. The scorecard is queryable mid-run — cost-to-date, pass rate by unit type, and units currently stuck in retry are all live numbers, not a post-hoc report.
